# 데이터 가정 (팀 결정 사항)

원본 `data/raw/stations.xlsx`(교수님 제공)는 수정하지 않는다. 원본에 없는 정보는 이 폴더의 파일로 보완한다.

| 파일 | 내용 | 근거 |
|---|---|---|
| line_stations.csv | 노선별 역 순서 (1·6호선은 순환) | 원본에 노선 열이 없어 노선도를 보고 작성, 원본 139개 구간과 대조 완료 |
| lines.csv | 순환선 여부 | 노선도 |
| transfers.csv | 환승역 35개, 환승 1회당 300초 | 팀 결정 (모든 환승역 동일) |
| station_names.csv | 역 이름 (한국어·영어) | 서울 실제 역명을 노선별로 빌려 배치. 실제 위치·순서와 무관한 가상 배치 |
| ai_facilities.json | 역·언어별 주변 시설 **예시** (아래 "주변 시설") | Gemini가 만든 가짜 예시. `scripts/generate_facilities.py`로 만든다 |

- 모든 구간은 양방향이며, 두 방향의 시간·거리·비용이 같다고 가정한다 (원본에 방향 정보 없음).
- 시간 단위는 초, 거리는 미터, 비용은 원 (원본 열 이름 기준).
- 경로 비용은 구간 비용의 합으로 표시한다. 실제 요금 규칙은 적용하지 않는다.
- 거리(미터)는 원본에 있지만 API 응답에 넣지 않는다 (팀 결정 2026-11-05).
- 즐겨찾기는 휴대폰(앱)에만 저장한다. 서버 DB에는 즐겨찾기 테이블을 두지 않는다 (팀 결정 2026-11-06).
- 역 번호 앞자리로 노선을 추정하지 않는다 (8개 구간에서 틀림). 노선은 항상 line_stations.csv 기준.

## 모임역 추천 확정 사항 (2026-11-17)
- 참여자는 2~4명이며 같은 출발역을 여러 번 선택할 수 있다. 각각 별도 참여자로 합산한다.
- 후보는 등록된 모든 역이며 출발역도 포함한다. 모든 참여자가 도달 가능한 후보만 평가한다.
- time: 개인별 최단 시간 탐색 기록의 시간 합계를 최소화한다.
- transfers: 개인별 최소 환승 탐색 기록의 환승 횟수 합계, 해당 경로 시간 합계 순으로 비교한다.
- fairness: 개인별 최단 시간 탐색 기록의 최대 시간, 시간 합계 순으로 비교한다 (minimax).
- 위 점수가 모두 같으면 숫자 역 번호가 작은 역을 선택한다.
- 최초 탑승·마지막 하차는 환승이 아니다. 자신의 출발역은 0초·0회다.
- 모임역 추천에서는 요금을 계산·반환하지 않는다. 기존 /routes 요금 응답은 유지한다.

## 방면 안내 확정 사항 (2026-11-17)
- 최초 탑승 및 환승 후 각 이동 구간의 다음 역을 방면으로 안내한다.
- 순환선도 실제 경로의 다음 역을 사용하며 역 번호나 종착역으로 방향을 추측하지 않는다.
- direction은 다음 역 번호이며 API에서는 요청 언어의 역 객체로 반환한다.
- 이동 구간이 없으면 방면 안내도 없다. 종착역행, 승강장 번호, 내선/외선은 제공하지 않는다.

## 주변 시설 (팀 결정 2026-11-18)
- 가상 노선이라 실제 주변 시설 데이터가 없다. 역 이름만 실제 서울 역에서 빌려, Gemini가 **예시**를 만든다. 실제와 달라도(가짜여도) 된다.
- 종류는 5개, 종류마다 1개: 카페(cafe), 음식점(restaurant), 편의점(convenience_store), 약국(pharmacy), 공중화장실(restroom). 각각 이름(name)과 위치 안내(detail, 예: "2번 출구 · 도보 3분").
- 주변 시설은 AI가 만든 예시다. 앱 화면에는 이 사실을 표시하지 않고, API의 `ai_generated` 값으로만 구분한다 (2026-11-25 이진 결정). API 응답에는 계속 `ai_generated: true`가 들어간다.
- 역 + 언어별로 한 번 만들어 DB(`ai_facilities`)에 저장하고 다시 쓴다. 그래서 같은 역은 늘 같은 시설이 보인다.
- 한국어 목록을 먼저 만들고, 다른 언어는 그 한국어 목록을 번역한다 (항목 수·순서·종류는 그대로, 이름과 위치 안내만). 그래서 언어가 달라도 같은 가게다 (2026-11-25 이진 결정). 브랜드는 그 언어에서 쓰는 이름(스타벅스 → Starbucks / スターバックス / 星巴克), 역 이름은 영어 이름을 기준으로 옮긴다.
- `ai_facilities.json`에서 이 방식으로 다시 만든 역은 701 먹골, 705 모란뿐이다 (2026-11-25, 시연에 나오는 두 역). 나머지 109개 역은 언어마다 따로 만든 예전 목록이라 언어별로 가게가 다를 수 있다. 전부 다시 만들기: `.venv/bin/python scripts/generate_facilities.py --rebuild`
- 미리 만들어 `ai_facilities.json`에 저장해 공유한다 (`scripts/generate_facilities.py`). `load_db.py`가 이 파일을 DB에 넣는다. 캐시 DB는 컴퓨터마다 따로라서, 파일로 공유해야 모두 같은 시설을 보고 Gemini도 한 번만 부른다. 파일에 없는 역·언어만 서버가 요청 때 만든다.
- 설명용과 다른 Gemini 키(`GEMINI_FACILITY_API_KEY`)를 쓴다. 비어 있어도 설명용 키로 대신 쓰지 않는다.
- 경로·모임역 AI 설명에는 여전히 주변 시설을 말하지 않는다 (데이터에 없는 내용이므로).

## 챗봇 (팀 결정 2026-11-23)
- 글로 묻고 답하는 챗봇을 넣는다. 길찾기 요청과 지하철 이용 안내(표 사기, 개찰구, 분실물 등)를 다룬다.
- **외부 AI(Gemini)를 부르지 않는다.** 무엇을 묻는지는 직접 만든 작은 모델(나노 모델, C++, CPU)이 고르고, 경로는 기존 계산 코드가 계산하고, 답 문장은 미리 써 둔 고정 문구만 쓴다.
- 모델 파일은 받은 그대로 `backend/app/chat/nano/`에 둔다 (v5, 2026-11-19). **이 폴더 안의 파일은 고치지 않는다.** 새 판을 받으면 폴더째 바꾼다. 우리가 고치는 곳은 `backend/app/chat/`의 나머지 파일이다.
- 모델은 한국어·영어 문장으로만 학습됐다. 답 문구도 한국어·영어부터 만든다.
- 학습 원본(`SF5_d128L4.pt`)과 학습 코드는 저장소에 넣지 않는다 (서버 실행에 필요 없음).
- 대화 내용은 서버(DB·로그)에 남기지 않는다. "그럼 반대로는?" 같은 이어 묻기에 필요한 직전 출발·도착역은 앱이 들고 있다가 다음 요청에 함께 보낸다 (`POST /chat`의 `context`).
- 앱도 대화를 저장하지 않는다. 대화는 챗봇 화면이 열려 있는 동안만 있고, 화면을 닫거나 "새 대화"를 누르면 사라진다. 챗봇에서 찾은 경로는 최근 검색에 넣지 않는다.
- 오타·줄임말로 쓴 역은, 맞는 역이 하나면 그 역으로 답하면서 "‘신도릠’ → 신도림 (이 역으로 이해했어요)"라고 알려 주고, 여럿이면 어느 역인지 되묻는다. "맞나요?"처럼 예/아니요로 확인받지는 않는다 (모델이 "네"·"아니요"를 알아듣지 못한다).
- 한국어·영어가 아닌 언어로 물으면 모델의 판단을 쓰지 않고 "한국어나 영어로 물어봐 주세요"라고 답한다 (모델이 그 언어들을 자신 있게 틀린다).
- 답 문구는 `data/chat/replies.json`에 둔다 (한국어·영어). 첫차·막차와 실시간 정보는 "이 앱에 정보가 없다"고 답한다.
- 챗봇 화면의 글자(제목, 입력창 안내, 예시 질문)는 한국어·영어 두 가지다. 앱 언어가 한국어면 한국어, 아니면 영어로 보여 준다 (챗봇이 두 언어로만 답하므로). 다른 화면의 번역과는 따로다.
- 챗봇으로 들어가는 버튼은 홈 화면 위쪽, 언어 선택 왼쪽에 둔다.
- 진행: 3단계(앱 챗봇 화면, `app/lib/screens/chat_screen.dart`)까지 됨. 설명: `docs/chatbot.md`, API는 `docs/api-spec.md` 4-2장
